# Luma: current UI/UX review

Reviewed 13 October 2026 against the running Android app and repository HEAD `8bff2e4`.

The app has a coherent palette, clear capture choices, persistent editor headings, and useful safeguards. The main remaining problem is hierarchy: browsing a day or understanding a week takes too much reading and scrolling. Date context and accessibility also need attention before further visual polish.

This is a fresh review of the current interface. The older `audit.md` contains findings that have since been addressed; those are not automatically treated as current defects here.

## Method and scope

- Live device: `emulator-5554`, `com.luma.lifeos`, 1080 × 2400, Asia/Tehran.
- English main flows; Persian RTL settings, Today, Timeline and mood form; French settings and Timeline.
- Light mode, dark Today/Timeline, and English font scale 1.3.
- Screenshots and accessibility XML are in `/tmp/luma-ux-review/`. Screenshot identifiers below name files in that directory.
- Existing records were opened; blank forms and confirmation dialogs were inspected. No life record was saved, updated or deleted. Backup export/restore and provider permissions were not executed. Existing enabled integrations can refresh themselves during normal app use.
- Save/error/retry, journal reading, photo rendering and dense-list behavior were additionally reviewed in source. These are not substitutes for live end-to-end tests.
- The emulator continued to show a floating handwriting toolbar even after temporarily changing keyboard settings. Conventional docked-keyboard behavior and TalkBack speech were not verified.

## Recommended changes and acceptance criteria

### 01 — Make the capture date explicit

Reproduction: Timeline → Previous → Quick Capture → Memory → More details. The timeline shows 12 October, but the draft shows 13 October. This is current behavior, not proof of an incorrect persisted timestamp: a global capture can intentionally mean “now.” The issue is that the UI does not tell the user that before they begin writing.

Show an editable “Today, 16:40” date/time line in every capture form. When browsing another date, make “Add to this day” available explicitly, or offer the browsed date as a deliberate choice. Keep time/timezone validation intact. Also reconsider the fixed “Today” heading when that tab is displaying a past day; `38-today-past` shows this ambiguity.

**Accept when:** users can identify the intended save date without expanding optional context, and past-day capture has a clear, tested policy across all three editors.

### 02 — Give each import switch its own name

The screen-time and health switches expose separate clickable, checkable nodes with empty text and content description. Their adjacent labels are separate nodes. Both read visually as “Enable imports,” so the accessible name also needs the integration context. The Timeline switch already supplies a content description and is a useful comparison.

Use one labeled toggle row or provide a localized accessible name such as “Enable screen-time imports” / “Enable step imports.” Preserve checked state, disabled state and keyboard interaction. Verify the actual spoken result with TalkBack.

**Accept when:** focusing either switch identifies both the feature and its current state. Android's [Compose semantics documentation](https://developer.android.com/develop/ui/compose/accessibility/semantics) explains how semantics convey an element's role, meaning and state.

### 03 — Preserve the filter through every timeline read

The normal page read passes `current.showAppUsage`. The count-change reread and empty-offset recovery omit that argument, while `TimelineRepository.page` defaults it to `true`. A fallback can therefore insert app-usage rows while the switch remains off and use a count from a different filtered population.

Pass the same visibility choice to both fallback reads. This risk is identified in source; the live install did not have the dense/concurrently changing day needed to exercise it safely.

**Accept when:** regression cases cover a count-changing pagination request and recovery after deleting rows beyond an anchor, with mixed manual/app-usage records and visibility off.

### 04 — Correct directional icons

Previous and Next both render `ic_chevron`, which contains a left-pointing path. In Persian, auto-mirroring makes both point right. The actions change dates correctly; the pictures do not describe the actions. Weekly Review uses the same icon for both directions.

Use distinct backward/forward icons with deliberate RTL behavior.

**Accept when:** each pair points in opposite directions in English and Persian, while preserving the localized accessible labels and correct date transitions.

### 05–06 — Put the day and its entries ahead of metadata

At font scale 1.3, the summary spans approximately y=507–1460 and the first entry starts near y=1645. Only a small portion of that entry is visible above the capture/navigation area. A populated mood card in Timeline is roughly 300 dp tall at normal text size because score, emotion, energy, stress, links, memory action, edit hint and source each add vertical weight.

Reduce the default summary to the most useful daily metrics, keeping a concise partial-history indicator. Put additional counts, top-app breakdown and explanations behind an explicit summary expansion. Use compact timeline rows/cards: type + time, primary content, a short context line, then details on open. Keep important text available to large-text users through wrapping and scrolling; do not solve density by shrinking fonts.

**Accept when:** a representative day exposes meaningful entry content in the first viewport at normal and larger text size, and users can scan several short entries without opening them.

### 07 — Separate reading from editing consistently

`openEvent` opens a journal detail screen but sends editable moods and memories directly to editors. Browsing a life record becomes a form task, and those editors display Delete next to Save. This is especially distracting from Search and Review.

Give manual records a consistent reading state with an explicit Edit action. Keep direct editing as an intentional shortcut if useful. Keep memory marking available without duplicating the record.

**Accept when:** tapping a record from Today, Timeline, Search, People and Review follows a predictable read → edit flow.

### 08 — Give Review an overview before evidence

The header explains saved observations, comparison dates, timezone and partial-week rules before any result. Every count then repeats current/previous labels, change copy and two source actions, including a zero-versus-zero journal card. The compact-card changes helped, but the overall screen still demands substantial reading.

Start with a concise week overview and section navigation for Mood, Memories, People/Places, Usage and Activity. Use compact comparisons with a secondary source action. Expand methodology, coverage and detailed daily evidence on request. Keep partial-week, missing-value and saved-observation distinctions explicit; do not invent causal insights.

**Accept when:** users can find how they felt, a notable memory and the main recorded activity/usage result without scrolling through all count/evidence cards.

### 09, 15 — Clarify Settings and catalog navigation

Language selection and a large backup card come before import controls. The same Settings list then becomes a day-based usage report. Places is a small text action in Settings, while People is a primary destination. A person has shared history, but an otherwise comparable place detail only shows name/note/coordinates.

Use concise Settings rows for Language, Backup, Privacy and Integrations, opening focused pages. Give saved usage a deliberate entry from Review or Timeline. Expose Places alongside People, such as a People/Places catalog switch, and consider a linked-entry history for places.

**Accept when:** a user can find an integration or a saved place from a clearly labeled entry, and configuration pages do not require scrolling through a usage feed.

### 10, 16 — Make capture choices understandable

The initial mood scale only shows 1–5. Accessible labels contain “Very low” through “Great,” but sighted users only see a description after selecting. Add visible low/high anchors or understandable labels that retain the compact layout.

Replace generic “More details” copy with a hint about its contents, or smaller sections such as “Note and context” and “People, place and photos.” Mood notes currently require this expansion, while journal/memory body text is immediately visible. Date/time should remain visible independently of context expansion.

**Accept when:** a new user can understand the mood scale before tapping, and can find notes, attachments and date controls without guessing.

### 11 — Keep rejected tag input in the journal flow

The Save handler attempts to add pending tag text, then calls `onSave()` regardless of whether `onAddTag()` returns false. At the tag-count limit, a nonblank new tag can be rejected, after which saving can leave the editor without that tag. `save()` also clears the error when starting a write. The previous tags/body remain valid, but the user's pending input is not represented in the saved record.

Stop the save attempt when adding a pending tag fails. Keep the text, associate the error with the tag field and bring it into view. Handle field-length errors similarly rather than showing all errors only at the top of a scrolled form.

**Accept when:** exceeding the tag limit preserves the unsaved tag and keeps the editor open with a clear correction path. This case was reviewed in source, not executed against a real journal.

### 12 — Align paging with the newest-first UI

The auto-loader calls `loadLater()` when the last visible key is `"later"`, but that key belongs to the top “Later events” control, which calls `loadEarlier()`. The bottom “Earlier events” control uses `"earlier"`. This can miss the automatic-load trigger when the bottom control is last visible, and can request the opposite end when the top control is last visible. Manual paging buttons are still available.

Watch the actual older-record boundary and retain a stable visible anchor when trimming the bounded window. Rename directional concepts where necessary to make chronological direction distinct from offset direction.

**Accept when:** a 300+ row day can be browsed in both directions without unexpected loading, gaps, duplicate rows or loss of the visible entry. The small live dataset did not establish this behavior.

### 13–14 — Improve search and feedback visibility

Search displays a filter count but selected people/place/date/tag names remain inside the dialog. Add removable active-filter chips and an explicit reset state. Its text search covers titles and linked names/tags, not journal bodies; that scope is partly explained already. Consider body search only if finding remembered writing is a product requirement, and keep the scope explicit.

Add heading semantics to important sections and accessible error/update announcements where appropriate. Make errors visible near the triggering field/action. Preserve existing retry and draft retention. Validate with TalkBack rather than treating source inspection as an accessibility pass; Android's [semantics guidance](https://developer.android.com/develop/ui/compose/accessibility/semantics) covers headings, errors and live updates.

**Accept when:** users can tell why results are filtered without opening a modal, and important validation/error changes are discoverable visually and with assistive technology.

### 17–18 — Standardize secondary browsing

Today uses hours/minutes while saved usage and Review show fractional seconds. The difference is rounding, not evidence that the underlying totals disagree. Use consistent human-readable precision, reserving exact intervals/values for details and preserving small nonzero durations.

Timeline is newest-first, while Review sources are oldest-first (`ORDER BY occurred_at, id`). Either align them or visibly indicate the sort policy. Detail screen Back/Edit rows live inside scrollable content; use a persistent top app bar, matching the existing editor pattern.

**Accept when:** duration displays and sort order are predictable across related screens, and users retain a visible way to leave/edit a long detail page.

## Recommended sequence

1. Address date clarity, accessible import labels, directional icons, and the source-level filter/tag/paging risks.
2. Simplify Today and Timeline density; standardize entry reading versus editing.
3. Restructure Review and Settings around the user's next task.
4. Improve filters, catalog discoverability and secondary detail consistency.

Keep the current privacy model, local capture, unsaved-change confirmations, import-retention explanations, language support, and distinction between missing measurements and recorded zero.

## Remaining validation

This review does not certify every possible state. Follow-up needs a conventional software keyboard, TalkBack, landscape/small-device and more extreme text sizing, dense timelines, populated journal/photo records, process recreation with drafts, injected load/save errors, and backup/restore/provider outcomes in an isolated test install. No app-code changes or automated test runs were part of this review.

The original English language, light theme, font scale 1.0, keyboard settings, selected day and Weekly Review screen were restored. Final evidence is `56-restored.png` / `56-restored.xml`. Existing repository changes and the older audit were preserved.
