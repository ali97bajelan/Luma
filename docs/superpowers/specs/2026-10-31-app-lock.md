## Authority and delivery

This specification converts the linked product requirements into a traceable execution contract. The four explicit user requirements are mandatory: a Luma password, selected sections or whole-app coverage, every-time or timed relocking, and password-free creation. The product document remains the source of intent; this document owns requirement IDs and shared contracts for the new plan. The 26 October F06 spec/plan/QA are historical inputs, not concurrent execution instructions for this revision.

Working planning baseline: adopt the product document's proposed recovery code, eight sections, per-section grants, Every time default, 1/5/15-minute options, screenshot protection initially on, and no people/place linking during restricted capture. These are stated planning assumptions, not a claim of separate user approval. No implementation or security validation is performed by generating this package. A change to recovery policy requires revising R02/R10 and their QA before that source work begins.

Exactly two phases per task: **Implementation**, then **QA**. For this app-lock package the user's scheduling instruction overrides the default per-task serialization in [WORKFLOW.md](../../feature-roadmap/WORKFLOW.md): finish all implementation handoffs before QA. A task's implementation depends only on predecessor **source handoffs**, never predecessor QA results. QA may remain NOT RUN while later source work progresses. QA completion remains required for acceptance/release; this rule is not a quality waiver.

During Implementation: production/config/resources/docs and source review only; no test authoring, Gradle/sync/resolution/build/lint/schema export, tests or device work. During QA: author tests/adapters, run checks, generate schemas where needed, use isolated devices, fix defects and retest. No third defect-fix phase. Keep API28 minimum, compile/target35, Java17, offline behavior, EN/FR/FA/RTL/light/dark, existing data/draft/media/revision contracts, and Android-free `core:domain`. Do not upgrade dependencies/platforms incidentally.

### Exact lifecycle and access decisions

Each process starts Unknown until policy/credentials load, then Disabled, Locked or Error; Unknown/Error cannot reveal private data. Lock state must distinguish initialization failure from an intentional disabled setting. Grants live only in memory, scoped by process/policy generation and section; Whole app uses a distinct whole-app grant. Do not serialize secrets or grants into navigation, intents, drafts, archives or restored state.

Timed mode counts away when no Luma activity is visible. At elapsed duration >= interval, revoke all grants existing at departure; cold restart always revokes. Wall-clock changes do not extend it. Rotation, locale/theme changes and an in-process activity replacement are not departures. Split-screen focus loss while a Luma activity remains visible is not departure. System authentication UI cannot trigger prompt loops. Device lock and explicit Lock now revoke immediately. Foreground inactivity alone does not relock.

Every time: a mixed-list unlock remains valid while scrolling, filtering, paging and navigating its related details/editors. A top-level destination change, settings navigation or restricted capture revokes selected-section grants. An unrelated detail revokes the grants it does not need. Related detail → parent does not revoke. A mixed-list unlock action asks which sections to grant. Multi-section objects request all required sections explicitly in one prompt; success grants only those sections. Timed mode keeps foreground grants across navigation. Entering restricted capture never extends/pauses a deadline or grants new access, regardless of its window/activity visibility.

A marked mood/journal inherits Memories protection for its entire source entry and media. People protection independently redacts linked identities and relationship metadata; do not redact arbitrary manually typed prose automatically. Mixed views must not leak protected counts, dates, pagination totals, filter options or search facets. A hidden summary or a labeled authorized-only summary is acceptable. Always refresh projections when grants change, including already loaded lists, photo viewers and accessibility semantics; reject old async results by policy generation.

Restricted capture starts with new input and an internal create identity. The only accessible data is that session's unsaved fields/new media; there are no old people/place selectors, saved suggestions, private templates, existing-photo browser, share/undo/open actions or existing habit logging. Its completion bypasses the ordinary `LifeOsApp` saved-result flow that fetches the saved record/date. Repeated save uses one operation identity; an existing-record collision is never an update or an informative error. Save authorization is checked at commit time, not only on entry.

Uninterrupted capture input survives rotation and its own picker/camera return. Genuine departure, device lock or process death hides the prior draft. Resume needs unlock; starting blank preserves the old draft separately. Ordinary existing-record editor drafts remain private when a grant expires. Picker return does not revive an expired browsing grant. Completed input/secrets are cleared; cancelled attachment cleanup is limited to owned new media.

Protected external previews remain generic even with an in-app grant. Apply immediately on enable/coverage change, including existing posted notifications and widget refresh. Do not promise launcher-cache or previously shared-file erasure. Recents masks protected content and restricted drafts independently of the screenshot switch. Password/recovery-code screens always block screenshots; the ordinary switch governs protected content/capture and defaults on. Generic safe pending actions are revalidated for ID/revision/expiry/policy generation and confirmed before mutation; at most once, never blindly replay destructive actions.

Security operation authentication is fresh, scoped to exactly one pending operation and consumed once. Opening settings is not blanket authorization to change policy later. Secret-policy writes/credential changes revoke grants. Missing/corrupt stores fail closed. Passwords/code verification use a reviewed established design; never store plaintext or reversibly recoverable passwords. Engineering records derivation/key protection, memory handling and reboot-safe retry accounting in T02's source handoff before implementation of that adapter; no invented crypto or unreviewed dependency.

Password and recovery attempts share a consecutive-failure counter. Failure 5 imposes 30,000 ms; each subsequent eligible failed attempt doubles delay to a maximum 900,000 ms. Submissions during cooldown do not verify a secret or change the counter. Successful verification resets it; restart/reboot cannot simply clear it. No automatic erase or permanent lockout. Code recovery atomically replaces password and code, consumes the old code only on success, revokes grants and returns locked. Interrupted recovery preserves the former credential pair.

Ordinary reset requires fresh password; forgotten-password reset is the sole unauthenticated reset exception. It has two explicit destructive confirmations, can only erase all local records/media/drafts/credentials, and never grants read/export/restore access. Existing backups are unaffected. Restore into a protected installation requires fresh auth and retains destination policy; fresh installs explicitly choose protection or no protection before any restored content is revealed. The app-lock password is not a backup-encryption password.

## Shared contracts and ownership

These are proposed Kotlin contracts, not declarations claimed to exist. T01 records the final signatures and all later source handoffs consume the same versions. Prefer facades/adapters over changing every existing repository's public signature. Trusted imports/background work use explicit internal capabilities; bypass paths must not be reachable from UI, intents or public components.

Domain package: `com.luma.lifeos.domain.lock`.

```kotlin
enum class LockSection { MEMORIES, JOURNAL, MOOD, TASKS, HABITS, PEOPLE, FOCUS, HEALTH_USAGE }
enum class LockCoverage { WHOLE_APP, SELECTED }
enum class RelockMode { EVERY_TIME, AFTER_1_MINUTE, AFTER_5_MINUTES, AFTER_15_MINUTES }
data class LockPolicy(val enabled: Boolean, val coverage: LockCoverage,
    val sections: Set<LockSection>, val relockMode: RelockMode,
    val screenshotsProtected: Boolean, val generation: Long)
enum class LockOperation { READ, UPDATE, DELETE, CREATE, SHARE, EXPORT, BACKUP, RESTORE, RESET, SECURITY_SETTINGS }
data class LockRequest(val operation: LockOperation, val requiredSections: Set<LockSection>,
    val objectId: String? = null, val createSessionId: String? = null)
sealed interface AccessDecision // Allow, NeedUnlock(sections, wholeApp), Deny
interface LockAccess {
    val snapshot: kotlinx.coroutines.flow.StateFlow<LockSnapshot>
    fun decide(request: LockRequest): AccessDecision
}
```

`LockSnapshot` contains load status (UNKNOWN/READY/ERROR), policy, in-memory section/whole-app grants, active browsing context, away deadline and session generation; no secret. `decide` must be pure against that snapshot; commit paths also revalidate under an execution guard immediately adjacent to persistence so a concurrent revocation cannot leave a stale authorization window. UI denial is not that guard.

App package: `com.luma.lifeos.lock`. T02 owns `LockCredentialService` with suspend `enable(password: CharArray, policy: LockPolicy, recoveryConfirmation: RecoveryConfirmation): CredentialResult`, `verify(password: CharArray, purpose: AuthPurpose): CredentialResult`, `changePassword(proof: OperationProof, replacement: CharArray): CredentialResult`, `recover(code: CharArray, replacement: CharArray, confirmation: RecoveryConfirmation): CredentialResult`, and `disable(proof: OperationProof): CredentialResult`. Remaining suspend signatures are `prepareRecovery(): RecoveryPreparation`, `confirmRecovery(preparation: RecoveryPreparation): RecoveryConfirmation`, `replaceRecoveryCode(proof: OperationProof, confirmation: RecoveryConfirmation): CredentialResult`, and `updatePolicy(proof: OperationProof, policy: LockPolicy): CredentialResult`. Preparation supplies a display-once generated code and an opaque handle; confirmation records explicit acknowledgment that it was saved. Preparation failure is an unavailable result/exception handled without enabling lock; neither type is serializable. `CredentialResult` has Success (with a proof only for successful verification), InvalidInput, Incorrect, Cooldown (with remaining milliseconds), Cancelled and Unavailable variants. `AuthPurpose` distinguishes BROWSE, OPEN_LOCK_SETTINGS, CHANGE_PASSWORD, CHANGE_POLICY, DISABLE_LOCK, REPLACE_RECOVERY_CODE, SHARE, EXPORT, BACKUP, RESTORE and RESET. Handles/proofs are opaque, process-local, purpose/generation-bound and nonserializable; the BROWSE proof is additionally bound to the exact requested section set or whole-app request held by the coordinator. Changing that pending request requires fresh verification. A display-only setup handle must not enable policy before recovery confirmation. Recovery code is verified within `recover`, not an independent read/unlock method. Never include secret/record content in messages.

T03 owns `AppLockCoordinator`: `onVisibleActivityCountChanged(count: Int, elapsedMs: Long, restrictedCapture: Boolean)`, `onDeviceLocked()`, `onNavigationChanged(context: LockBrowseContext)`, `lockNow()`, `onPolicyChanged(policy: LockPolicy)`, `unlock(proof: OperationProof, sections: Set<LockSection>, wholeApp: Boolean)`. Internal activities/config changes are reconciled before declaring no visible activities. The coordinator implements `LockAccess`; snapshot Unknown is present before any data navigation draws. It also owns the serialized action guard consumed by T04/T05/T07/T08; operations must distinguish a started commit from a future action revoked before start.

T01 owns `ProtectedRecordClassifier.requiredSections(record: LifeEventRecord): Set<LockSection>`. T04 consumes it and owns `ProtectedContentGateway`, the only UI-facing facade over existing repository/summary/media operations. It produces redacted projection types, not full protected records later hidden by composables. Cover non-event tasks, habits, people and Focus as well as event graphs. Keep trusted repositories injected privately; do not expose raw repository references to restricted editors.

T05 owns `RestrictedCaptureService.begin(kind: CaptureKind): CreateSession`, `save(session: CreateSession, input: CaptureInput): CaptureResult`, `cancel(session: CreateSession)`, plus private multi-draft storage. `CaptureKind` is MEMORY/JOURNAL/MOOD/TASK/HABIT_DEFINITION. `CreateSession` is process-owned authority with a durable idempotency identity; restored draft IDs alone confer no authority. `CaptureInput` is the corresponding existing domain input, with links/private templates disallowed; results are Saved, ValidationError, RetryableFailure or Conflict without old-record data. Durable create receipts and draft metadata must not transfer authentication capability.

T07 owns `ProtectedPreviewPolicy` and `ProtectedActionDispatcher`; T08 owns `LockSensitiveOperationGuard` using one-operation proof and existing backup/share/reset services. Their final signatures are recorded by their owning task; callers consume the decision/proof/guard contracts above rather than duplicate authentication.

## Source boundaries and acceptance

Reuse existing navigation, repositories and editor contracts. Add no fixed Room/archive version in this plan: inspect the execution baseline and allocate only if private draft/receipt storage actually needs a migration. No schema export in Implementation. Extend existing reset, archive adapters and photo ownership instead of creating competing mechanisms. There must be an inventory mapping each raw UI repository injection/caller to an authorized facade or a justified trusted-background role.

All LOCK-R01–R12 require a source handoff, scenario result and exact test/manual evidence. Product AL-01–AL-22 are retained one-to-one as AL-Q01–AL-Q22 in the new QA document. Baseline/default assumptions, unknown compatibility and blocked scenarios stay visible. Only whole-feature acceptance may claim that lock is safe across all content and entry paths. No individual source handoff or partial host pass is release acceptance.
