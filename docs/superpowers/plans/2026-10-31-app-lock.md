# App lock v2 Implementation Plan

> **For agentic workers:** REQUIRED SUB-SKILL: Use superpowers:executing-plans to implement this plan task-by-task. Use delegation only when separately authorized. Steps use checkbox (`- [ ]`) syntax for tracking. The user's two-phase schedule overrides test-first steps: tests are authored and executed only in QA.

**Goal:** Implement a user-defined Luma password, whole-app or selected-section coverage, configurable relocking and isolated password-free creation.

**Architecture:** Pure domain access/timing contracts feed one process-local coordinator and a serialized authorization guard. UI-facing secured facades filter/redact repository projections, while restricted editors receive only create-session authority; credentials and private drafts remain device-local. Integrate existing navigation, media, background work, external surfaces and archive/reset services rather than introducing a second app shell.

**Tech Stack:** Existing Kotlin/coroutines/Flow, Room where required, Compose/Material3, Android local storage and elapsed realtime, Java17. Record credential-adapter choices in T02; do not add an unreviewed dependency or implement custom cryptography.

**Spec:** [App lock execution specification](../specs/2026-10-31-app-lock.md)

## Global constraints

- Minimum API28, compile/target35, Java17; keep `core:domain` free of Android/Room.
- Exactly two phases per card. **Complete all implementation handoffs first, then QA.** Implementation prerequisites are source handoffs only, never predecessor QA PASS. No source-complete card is feature-complete.
- Implementation: no tests authored/executed, Gradle/sync/resolution/build/lint/schema export, emulator/device use. QA owns those activities and defect correction. Static source/XML/JSON/link/whitespace checks are allowed during implementation.
- Preserve personal data/edits/release artifacts, drafts, media ownership, revision/idempotence checks, EN/FR/FA/RTL/light/dark/accessibility. Calendar remains tasks/memories only; main navigation remains Today/Timeline/Calendar/Review/More.
- Do not assign fixed Room/archive version numbers until execution; serialize source migrations and export/validate schemas only in QA. No destructive migration, network requirement, analytics or restored authentication capability.
- New spec supersedes conflicting 26 October F06 choices for this package. Recovery code and proposed defaults are explicit planning assumptions. A changed material product decision updates spec/scenarios/data before its owning implementation.

## Review focus

1. A list/search/photo response arrives after revocation: generation checking and secured projections prevent a private flash (T03/T04; Q03/Q05/Q22).
2. Restricted capture reuses a caller ID or ordinary saved-result callback: only its new record can be created and no post-save lookup reveals history (T05; Q09/Q10).
3. Two windows change policy or revoke while a save/action begins: serialized authorization and source revision checks define one commit boundary (T01/T03/T04/T07; Q10/Q12/Q17).
4. Capture resumes through a picker versus a genuine departure/process death: private draft visibility, retained media and no overwritten older draft (T05; Q08/Q11/Q12).
5. Recovery/cooldown/restore is interrupted or stores are corrupt: old credentials remain valid until atomic replacement, retry state survives restart, no fail-open/reset read bypass (T02/T08; Q13/Q15/Q18/Q19/Q22).
