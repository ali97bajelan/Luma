# App lock v2 Implementation Plan

> **For agentic workers:** REQUIRED SUB-SKILL: Use superpowers:executing-plans to implement this plan task-by-task. Use delegation only when separately authorized. Steps use checkbox (`- [ ]`) syntax for tracking. The user's two-phase schedule overrides test-first steps: tests are authored and executed only in QA.

**Goal:** Implement a user-defined Luma password, whole-app or selected-section coverage, configurable relocking and isolated password-free creation.

**Architecture:** Pure domain access/timing contracts feed one process-local coordinator and a serialized authorization guard. UI-facing secured facades filter/redact repository projections, while restricted editors receive only create-session authority; credentials and private drafts remain device-local. Integrate existing navigation, media, background work, external surfaces and archive/reset services rather than introducing a second app shell.

**Tech Stack:** Existing Kotlin/coroutines/Flow, Room where required, Compose/Material3, Android local storage and elapsed realtime, Java17. T02 uses the JCA PBKDF2-HMAC-SHA256 provider, Android Keystore HMAC, and AtomicFile; no new dependency or custom password KDF was added. See the T02 source handoff for the security tradeoff and review items.

**Spec:** [App lock execution specification](../specs/2026-10-31-app-lock.md)

- Minimum API28, compile/target35, Java17; keep `core:domain` free of Android/Room.

- Preserve personal data/edits/release artifacts, drafts, media ownership, revision/idempotence checks, EN/FR/FA/RTL/light/dark/accessibility. Calendar remains tasks/memories only; main navigation remains Today/Timeline/Calendar/Review/More.
- Do not assign fixed Room/archive version numbers until execution; serialize source migrations and export/validate schemas only in QA. No destructive migration, network requirement, analytics or restored authentication capability.
- New spec supersedes conflicting 26 October F06 choices for this package. Recovery code and proposed defaults are explicit planning assumptions. A changed material product decision updates spec/scenarios/data before its owning implementation.

## Review focus

1. A list/search/photo response arrives after revocation: generation checking and secured projections prevent a private flash (T03/T04; Q03/Q05/Q22).
2. Restricted capture reuses a caller ID or ordinary saved-result callback: only its new record can be created and no post-save lookup reveals history (T05; Q09/Q10).
3. Two windows change policy or revoke while a save/action begins: serialized authorization and source revision checks define one commit boundary (T01/T03/T04/T07; Q10/Q12/Q17).
4. Capture resumes through a picker versus a genuine departure/process death: private draft visibility, retained media and no overwritten older draft (T05; Q08/Q11/Q12).
5. Recovery/cooldown/restore is interrupted or stores are corrupt: old credentials remain valid until atomic replacement, retry state survives restart, no fail-open/reset read bypass (T02/T08; Q13/Q15/Q18/Q19/Q22).

- **Produced contract:** `LockCredentialService` with spec signatures plus `cancelRecovery`; `DefaultLockCredentialService`; `LocalLockStore`/`AndroidLocalLockStore`; `AuthPurpose`, `CredentialResult`, one-use `OperationProof`, display-once `RecoveryPreparation`, and opaque `RecoveryConfirmation`. BROWSE additionally binds the exact section set or Whole-app request. Changed requests invalidate an existing proof. - **Security/storage choice:** password code-point validation accepts 8–128 Unicode scalar values with exact UTF-16 input and no trim/normalization; PBKDF2-HMAC-SHA256 uses 600,000 iterations and a unique 128-bit salt, followed by a purpose-separated HMAC using a non-exportable Android Keystore key. Recovery codes use 128 random bits, uppercase Base32 grouped for display, a unique salt, and SHA-256; only the verifier is retained. The complete binary state is MAC-authenticated and committed with `AtomicFile` in `Context.noBackupFilesDir`. Android documents that directory as excluded from automatic remote backup ([Context reference](https://developer.android.com/reference/android/content/Context#getNoBackupFilesDir())); Android Keystore keys are non-exportable to the app process ([Keystore guide](https://developer.android.com/privacy-and-security/keystore)). OWASP lists Argon2id as its first choice for general password storage and PBKDF2-HMAC-SHA256 at 600,000 iterations for FIPS-required use; this implementation chose the built-in JCA PBKDF2 provider to avoid a new, unreviewed KDF dependency and does **not** claim FIPS compliance ([Password Storage Cheat Sheet](https://cheatsheetseries.owasp.org/cheatsheets/Password_Storage_Cheat_Sheet.html)).
- **Retry/atomic behavior:** password and recovery failures share one counter; failure 5 starts 30 s, doubles through a 15-minute cap; active cooldown blocks verification and counter changes. Same-boot time uses elapsed realtime; a changed boot marker conservatively starts a fresh 15-minute cooldown. Successful verification persists counter reset before returning a proof. Credential pair, code rotation, policy generation, and disable each use one authenticated atomic state replacement; the admitted state write and grant-invalidation callback run under `NonCancellable`. Since the callback follows the file commit, T03's guard must also compare the current persisted policy generation immediately before commit so a queued action cannot slip through the callback window. Corrupt/missing state with an existing Keystore key returns Unavailable. The MAC detects modification/corruption but is not an anti-rollback anchor; restoring an older valid payload is not detected by this store.
- **Revocation and requirements:** successful credential/policy changes increment policy generation and call the required T03 invalidation callback. Secret arrays are taken by ownership and cleared; verifier/proof/recovery handles are not serialized or logged. Maps to LOCK-R01/R02/R10/R12 and Q01/Q02/Q13–Q15/Q22.
- **Source checks:** read-only code review and static whitespace/newline check passed for all owned source/docs files; no tests, build, lint, Gradle sync, schema, or device operations, as required for Implementation. QA remains NOT RUN.
- **Ruling:** keep the exact service method signatures listed in the shared spec; exact operation UUID comparison is exposed as a mandatory claim step immediately before the mutation method, rather than adding UUID parameters that would fork that shared contract. Cost if wrong: a future T06 caller that validates an old UUID and then mutates changed form data without revalidating could apply proof A to a same-purpose mutation B; T06/T08 QA must cover request changes and one-use behavior.
- **Uncertainty / security review:** no independent security review or API28/API36 provider/performance validation has run. Validate PBKDF2 cost and Unicode vectors on supported Android providers; verify Keystore availability/recovery behavior and persistent cooldown after reboot; assess whether anti-rollback resistance is required. A process death in the narrow interval after first-use Keystore key creation but before the atomic state file commit leaves a missing-state/key mismatch and fails closed; QA must exercise this interruption and confirm the recovery path. T03 must verify the browse request captured before authentication is still pending before binding/consuming the proof. T06 must create a fresh operation UUID when its pending operation changes, capture it before showing password entry, verify the pending operation still matches and bind the returned proof after successful verification, validate the same UUID immediately before mutation, compare the two password entries before calling `enable`, explicitly collect final consent, clear the display array, and call `cancelRecovery` on cancellation. T08 must consume the matching operation UUID and keep archive/export/reset boundaries separate from this store.
