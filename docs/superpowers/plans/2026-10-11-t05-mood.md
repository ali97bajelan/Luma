# T05 mood check-ins implementation plan

**Goal:** Capture, edit, delete and browse local mood check-ins with multiple emotions and optional energy, stress, note and occurrence time.

**Architecture:** Add Android-free mood models and repository contract, a transactional Room implementation using the existing v1 tables, and a navigation-scoped editor with saved draft state. Extend the repository's daily observation to typed records so envelope and mood details arrive in one Room snapshot. Reuse the day feed for the initial Timeline and open manual mood rows in the editor.

**Spec:** `TASKS.md` T05; `ARCHITECTURE.md` domain and transaction boundaries.

## Constraints

- Keep existing tool/SDK versions, no permissions or network access, no schema change.
- Preserve unrelated event links, memory markers, media, and metadata when editing.
- Seed a reusable emotion catalog idempotently; multiple selections are optional.
- New captures default to now and require an explicit score selection; optional fields are collapsible. Timestamp gaps during DST must be rejected rather than shifted silently.
- Keep drafts through recreation, block duplicate submits, retain inputs on errors, confirm deletion and discarding changes, and do not recreate an event deleted elsewhere.
- Keep journal/memory capture and the full T11 Timeline outside this task.
- Run local JVM/build/lint checks, leave device execution to the user. Existing app lint incompatibilities may remain pending.

## Review focus

- Edits must preserve IDs/audit creation and unrelated aggregate content.
- DST gaps and overlaps, and moving an event to a different day, must be handled consistently.
- Save failure or recreation must preserve user input and prevent duplicate records.
- Imported/incomplete moods must never open a destructive edit flow.
- Existing catalog rows must remain intact on repeated initialization.

## Execution record

- Missing domain models/time conversion and editor state were verified by compilation failures before implementation. Domain and editor tests then passed.
- Review found restored dirty state lost before/after load failure, renamed seeds overwritten, and committed captures retaining an occupied create ID after process death.
- Two recovery JVM regressions failed before the fixes, then passed. Catalog rename preservation has a device regression source. Re-review found no important issues.
- Scope decisions: reuse a daily feed for Timeline now, keep T11 broader rendering/navigation/performance later; reject attached-media deletion until T10 owns physical cleanup; preserve the user's build versions and leave emulator execution to the user.
- Deferred validation: device capture timing, persistence/recreation flows, dialogs/back confirmations, large-font/landscape layout, and full app lint blocked by existing detector binary incompatibility.
