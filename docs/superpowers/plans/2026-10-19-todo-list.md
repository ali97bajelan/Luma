**Goal:** Let people capture, organize and finish one-time personal tasks offline, with a dedicated list and a bounded Today preview.

**Architecture:** Add a pure Kotlin `domain.todo` contract and one standalone Room table. Wire it through the existing `LumaStorage` composition root into Compose routes, using Flow for observation and revision-checked transactions for writes. Extend portable backup with the feature; tasks do not become life events or habit logs.

**Tech Stack:** Existing Kotlin/JDK 17, Coroutines/Flow, Room, Compose Material 3, Navigation Compose, SavedStateHandle, JUnit and AndroidX/Compose tests. No dependency upgrade.

**Spec:** [Product](../specs/2026-10-19-todo-product-spec.md), [UX](../specs/2026-10-19-todo-ux-spec.md). Read both before executing. [Task index](../../TODO_TASKS.md) owns delivery status.

## Global Constraints

- Native Android; minimum API 28; compile/target API 35; JDK 17.
- Local-first and offline; no account, network permission, telemetry or new runtime permission.
- English, Persian and French; preserve offline language switching, drafts and RTL layout.
- Title: trimmed, single line, 1–200 Unicode code points. Note: optional trimmed multiline plain text, maximum 4,000 Unicode code points; blank becomes null.
- Due date: optional ISO `LocalDate` in years 0001–9999; no due time, recurrence, reminder, priority, projects, subtasks or attachments.
- Retain Today · Timeline · Habits · Review · More. Tasks is a secondary destination under More.
- Today preview: at most three open tasks due on/before the actual device date; hide it when browsing another date; exclude undated tasks.
- Standalone task data never contributes to Timeline, existing entry counts, summaries, habit counts or weekly Review in this release.
- Preserve existing user changes. Read current source before editing: this planning checkout already has extensive uncommitted changes, and parts of `ARCHITECTURE.md` describe an older schema.
- Live database baseline is version 3. Planned version 4 adds one table; retain migrations and archive readers for versions 1–3.

## Review Focus

1. Ambiguous commit followed by retry must not duplicate a task or reverse a later completion/reopen: TD02 and TD04 pin revision and retained-operation behavior.
2. Returning after midnight or timezone travel must regroup open tasks and hide an out-of-date Today preview without changing stored due dates: TD05 and TD06.
3. Supplementary Unicode, Persian text, multiline paste and French expansion must preserve input and expose validation without truncation: TD01, TD04 and TD07.
4. Restore of an older archive must clear tasks, while corrupt/newer archives and cancellation leave current data untouched: TD03.
5. Row removal/reordering during completion, deletion or live pagination must retain usable focus, avoid duplicate actions and accurately show remaining tasks: TD05 and TD07.

## Contracts fixed by this plan

New files below are proposed names; existing paths were checked against the working tree on 19 October 2026. `K` means `core/domain/src/main/kotlin/com/luma/lifeos/domain/todo/`; `D` means `core/data/src/main/kotlin/com/luma/lifeos/data/`; `U` means `app/src/main/java/com/luma/lifeos/ui/`. Test paths follow the existing `src/test` or `src/androidTest` layouts named per task.

`TodoTask` has `id: UUID`, `title: String`, `note: String?`, `dueDate: LocalDate?`, `completedAt: Instant?`, `createdAt: Instant`, `updatedAt: Instant`, `revision: UUID`. Completion is derived from `completedAt != null`; do not store a second status flag. `TodoInput(title: String, note: String?, dueDate: LocalDate?)` is normalized/validated at the domain boundary. `TodoPage(items: List<TodoTask>, total: Int)` contains a consistent prefix and its full matching count.

```kotlin
interface TodoRepository {
    fun observeList(completed: Boolean, limit: Int = 50): Flow<TodoPage>
    fun observeToday(date: LocalDate, limit: Int = 3): Flow<TodoPage>
    suspend fun get(id: UUID): TodoTask?
    suspend fun create(id: UUID, initialRevision: UUID, input: TodoInput): TodoTask
    suspend fun update(id: UUID, expectedRevision: UUID, nextRevision: UUID, input: TodoInput): TodoTask
    suspend fun setCompleted(id: UUID, expectedRevision: UUID, nextRevision: UUID, completed: Boolean): TodoTask
    suspend fun delete(id: UUID, expectedRevision: UUID)
}
```

`TodoConflictException` and `TodoMissingException` distinguish conflicting changes from unavailable rows. Invalid text throws a typed validation error from `TodoRules`; the UI maps it to localized resources. Never show exception messages as user copy. Mutations use desired state, not a blind toggle. Retain one operation token across an ambiguous retry. A current row with the same operation revision and submitted values is an already committed success; otherwise a stale expected revision conflicts. A same-state completion request with the current expected revision is a no-op and preserves its timestamp. Delete of a missing row succeeds; a changed existing row conflicts. Do not recreate deleted rows from update or completion. Completion feedback offers Undo as a revision-checked reopen against that exact completion revision; an intervening change blocks it. Reopen and permanent deletion have no Undo contract.

List loading starts with an observed `LIMIT 50` prefix. Load more increases the prefix by 50 and reobserves a single ordered query/count transaction; do not concatenate shifting OFFSET pages. Open ordering is dated tasks first, due date ascending, creation time ascending, canonical UUID text ascending; undated tasks follow with the same tie breakers. Completed ordering is completion instant descending, UUID ascending. Group labels are derived from actual device today. SQL order and domain fixtures must agree.
