# App Lock Coverage Implementation Plan

> Execute with the Superpowers executing-plans workflow. Check off each step as evidence is recorded.

**Goal** — Offer Whole app and Memory section as the two coverage choices and keep everyday browsing responsive while Memory is locked.

**Architecture** — Keep AppLockCoordinator and ProtectedContentGateway as authorization owners. Filter mixed Room queries by visibility before counts and pagination, and start Memory-only work only after authorization.

**Tech stack** — Kotlin, Compose, coroutines, StateFlow, Room, existing authenticated lock storage, Android instrumentation and release-like performance tracing.

**Spec** — [App Lock coverage and Memory performance](../specs/2026-11-21-app-lock-coverage-design.md)

## Global constraints

- API 28 minimum, compile/target 35 and JDK 17. Keep the feature offline and the existing credential, archive and record formats. Only the App Lock policy encoding changes.
- Use the repository’s source-first App Lock workflow. Complete the source handoffs and static checks before authoring or running QA tests, invoking Gradle, or using an emulator or device. Run QA on the integrated candidate with a QA package and synthetic fixtures. [Delivery workflow](../../feature-roadmap/WORKFLOW.md) · [App Lock task board](../../APP_LOCK_TASKS.md)
- Use the existing Luma UI components and tokens, preserve App Lock behavior and editor invariants, and maintain EN/FR/FA, RTL, offline fonts, appearance modes, TalkBack, 48 dp targets, large text and existing insets.
- Preserve the existing repository entry points used by public UI and fixtures. The application alone translates a current lock snapshot into query visibility. A query flag carries no authorization to publish data or write changes.

## Review cases

- A legacy Mood-only or Memories + Tasks policy becomes Whole app and survives a credential write before its migration notice is shown (task 1).
- A mood that gains a Memory marker during a query becomes private. A late page result or preview cannot publish after relock (tasks 3 and 4).
- A Search restored with a stale Memory tag filter drops the filter while keeping the public query. A Place detail keeps its header and public events while its Memory history is filtered (tasks 3 and 4).
- A canceled widget or restored Memory destination clears the pending request and never opens an editor with a saved baseline (tasks 2 and 3).
- A Summary cached while unlocked is never shown through the locked projection. A Capture or background write revives neither the locked observer nor an obsolete grant (tasks 2, 4 and 5).
